## 用户及管理员使用

用户沿用邀请返利入口，五个页内标签为概览、我的邀请、收益记录、排行榜、邀请活动。普通邀请链接前置，活动分享继续使用原签名及团队归属机制。我的邀请和收益服务端分页，收益按来源及币种分别展示，到账关联已有钱包。活动保留报名、版本化奖励领取以及已参加和已结束记录。

邀请月榜、历史月份、活动榜和农场日/月榜用户接口仅返回前十名，本人排名独立。邮箱名与域名均脱敏，如 `al***@g***.com`；缺少有效邮箱交由本地化显示匿名用户。当前选中榜每五秒刷新，隐藏暂停、恢复立即、失败十/二十/三十秒退避。只刷新已入账排名，不承诺未入账用量实时计算。历史结算记录不反复拉取，前三领奖台及四至十名合计最多十人。

管理员保留邀请返利导航，新增运营概览；原邀请记录可切换全部推广用户。用户详情集中展示归属、付费资格、资金、活动关联和审计；返利与转出支持精确用户/受邀人/订单/活动/来源/币种/状态筛选、服务端汇总及最多一万条同条件CSV导出。线下提现仍为站外付款后的登记，补充外部流水号、付款时间、备注、操作者，同一幂等请求不能更换凭据。专属邀请码和比例原子保存，继承全局和专属值明确区分，敏感操作沿用JWT管理员step-up。限时活动继续在玩法运营管理。

来源有可靠关联时区分订单返利及活动奖励；旧非订单流水不能证明原始来源，标记其他/历史来源，不通过金额和时间猜成战队奖励。返利钱包可用额度是既有账户额度，不把活动币种与钱包额度当作新的汇率兑换规则。

## 数据与迁移

- `350_affiliate_operations.sql`：绑定时间、唯一受邀人的首付事实（规则版本 `paid-invite-v1`）、增量刷新触发器及业务审计；真实支付的余额和订阅订单作为来源，不计赠送、人工贡献或无订单证据记录。
- `351_affiliate_operations_withdraw_evidence.sql`：返利转出流水的凭据、付款时间、备注、操作者及索引，旧记录允许空值并明确历史未留存。
- 只新增迁移，不改历史已部署SQL。首付月份按上海时区固定；全退失效，重付恢复原月份，不跨月重复计人。多人归属冲突、归属晚于首付、历史证据缺失进入待核验，不能凭档案创建时间猜算。
- 历史证据不足不新增一键确认、改绑或补发入口。已有订单核验不能替代缺失的邀请先后证据。
- 查询只读首付事实；支付/绑定变更按单受邀人索引增量更新，不因五秒轮询扫描支付历史。
- 旧用户接口及管理记录路由保留；旧amount-only提现调用兼容，当前管理表单强制完整凭据。

新增用户查询位于 `/api/v1/user/aff/operations/{summary,invitees,earnings,leaderboard,campaigns}`，所有查询强制当前登录用户所有权。管理查询位于 `/api/v1/admin/affiliates/operations/*`；原三类记录增加 `/summary` 和 `/export`，同一过滤条件用于列表、汇总和导出。CSV防公式注入、保留大整数标识、包含过滤条件及实际时区，空结果也保留元数据。
