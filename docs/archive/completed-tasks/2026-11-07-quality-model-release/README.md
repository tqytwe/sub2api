## 管理员如何使用

1. 在质量运维创建/编辑规则，设置多个测试模型，失败动作选择“按模型隔离”，明确选择全模型失败时移除的分组。预设和分组模板也完整保留此配置。
2. 单模型明确答错仅隔离对应映射模型；全部测试模型明确失败才移除选定分组。原生限流、其他分组、账号 schedulable 和无关 Extra 不变。
3. 开启自动恢复后，每个模型全部配置样本明确通过才恢复该模型，任一明确通过可恢复本规则移除的分组；缺样本、跳过、未知不会释放限制。映射到同一模型时，失败/未知证据优先于通过。
4. 规则列表点击归属预览，查看逐模型影响/禁止原因；选择明确原因并确认，每次只移除一个测试模型及其对应标记/快照。孤立标记只允许精确属于本规则的标准标记；最后一个模型不可移除。
5. 释放后重新读取规则和预览，剩余模型、组快照、计数、原生限制和历史保持。需要整体退出时，对精确归属执行恢复，或在原值已恢复时对账；完成后再预览删除。整体恢复/对账会暂停并更新规则版本。
6. 过期预览、运行中任务、其他 owner、额外字段、同 owner 漂移、原有限制、歧义/共享映射、状态/分组冲突均保留原限制并给出原因。不会自动重试写入；先核对后刷新。

## 契约和并发

- 新增 `quality.action=isolate_models` 和 `remove_group_ids`；要求显式模型及 1–100 个唯一正数分组 ID。普通质量动作字段向后兼容。
- 隔离独立放在 `extra.quality_model_isolation`，标准 marker 仅 `reason=quality_rule:<id>`、`isolated_at`。不覆盖原生 cooldown。
- 新增管理员 POST `/api/v1/admin/scheduled-test-plans/:id/ownership/remove-model`，请求包含 `model`、`reason_code`、`confirm=true`、64 位十六进制 `fence`。原因仅 `orphan_marker_recovery` / `retire_model`。
- 预览只返回业务模型 ID、枚举、版本和摘要，不返回 credentials、Extra、提示词、原始限制或完整快照。
- fence 包含真实配置/计划行、state、完整 live Extra/credentials/平台/类型/状态/版本/过期、租约、完整组 membership 和相关组删除状态。任一变化均须重新预览。
- 保持 Fork 既有 account → plan → state 锁序；单模型变更与 outbox 同事务，失败全回滚。更新规则版本，过期 worker 不能把已释放的目标加回。
- 普通计划和模板更新也锁账号后重读 ownership，避免 UPDATE 的 NOT EXISTS 在等待行锁之前读取旧 MVCC 快照。真实并发测试已复现旧实现漏过新 state，修复后通过。
- 保持 account → plan → state 顺序；涉及分组时按 group catalog → memberships 加锁，与既有分组删除一致。真实 PostgreSQL 复现旧 membership → catalog 顺序与 DeleteCascade 死锁，改序后同测试通过；未修改分组删除功能。
- 普通账号保存从锁定的数据库行保留当前服务端隔离；局部和批量 Extra 写入丢弃外部隔离字段；创建/复制不携带旧归属。防止旧表单覆盖新隔离或复活已释放标记。真实 PostgreSQL 六种存在/缺失×保存/局部/批量场景先失败后通过。
- 单模型操作完成后验证规则范围和归属均已回读，再从当前规则的编辑草稿移除该目标，保留 Cron 等其他草稿。规则读取失败、预览失败、仍含旧目标均明确提示已提交但未确认，保留草稿且不显示成功。
- 质量内部/管理员复测使用私有 context 标记绕过质量隔离；普通请求不能从 header/payload 获取绕过权限，原生 cooldown 仍在。
