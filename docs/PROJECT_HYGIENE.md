# 工程状态与交接入口

> 状态：active · 维护责任：当前任务提交者；长期维护人待分配
> 本页定义维护方式，不是实时看板，也不扩大合并、部署或数据操作权限。

## 从哪里接手

| 要查什么 | 唯一维护位置 |
| --- | --- |
| 当前工作项、缺口、PR/SHA、验证与弃用记录 | [交接快照](./upstream-migrations/v2.10.3/handoff.json)，以其中 `checked_at` 为准 |
| 固定上游来源、分析基线与完整迁移标志 | [来源锁](./upstream-migrations/source-lock.json) |
| 固定版本差异、分批边界与路由分类 | [v2.10.3 迁移账本](./upstream-migrations/v2.10.3/README.md) |
| 已落地 Fork 不变量及自动保护 | [Fork 定制登记](./FORK_CUSTOMIZATIONS.md)，不把待实现项登记为已生效 |
| TDD、双审查、测试、合并、部署和最终验收 | [交付流程](./DELIVERY_WORKFLOW.md)；[上游同步手册](./UPSTREAM_SYNC_PLAYBOOK.md) |

快照仅覆盖已核查的本轮工作，不是全站功能目录或百分比进度。历史审计、文件/路由计数、
CI 成功、后端 DTO 或数据库测试均不能替代完整用户闭环。移动端/Canvas 排除在本轮之外。
接手人先重查 GitHub PR、head/base、CI 和部署证据，再决定下一步；文档年龄不自动触发发布。

历史状态使用不可变 Git 版本保留，例如 [2026-10-10 09:20:49 UTC 快照](https://github.com/tqytwe/sub2api/blob/6e3977e649a94a94cf880a010add6e23e1aae527/docs/upstream-migrations/v2.10.3/handoff.json)。
该版本记录当时的 PR351 阻断，当前状态仍只更新上表的同一快照；后续交接引用新旧 SHA，不复制另一份当前看板。

`production.branch_sha` 与 `last_verified_deployed_sha` 分别记录分支和最后确认的成功部署；
合并后仍在排队/部署时保留差异，不能据分支前进宣布上线，也不能假定旧版本仍在线。

## 状态与更新规则

每项分别记录 `backend_state`（条目限定的后端范围）和 `product_state`（完整用户闭环）。
它们不必同步；已部署能力仍可缺少生产验收，发现回归可降回实现中并记录原因。

| 值 | 使用条件 |
| --- | --- |
| 设计 | 需求/契约待定，没有足够实现证据 |
| 实现中 | 实现或修复未完，仍有功能缺口 |
| 可测 | 限定范围可运行/审查，测试或验收证据尚不完整 |
| 已验证 | 限定范围的适用验证通过；注明环境、SHA 与剩余非目标范围 |
| 已部署 | 精确 SHA 的部署成功有证据；健康和用户本机验收仍须单列 |
| 弃用中 | 已记录弃用决策，仍保留兼容行为/入口，尚未获准全部移除 |
| 已移除 | 明确批准的范围已移除，保留决策、迁移与必要历史回归证据 |

提交者在开 PR、head/base 变化、验证结果变化及部署/验收后更新同一记录；跨任务交接必须复核。
`checked_at` 是整份快照的核查时间，逐项检查后才前移；未复核条目在 `next` 明示。
PR 讨论保存详细过程，快照只保留结论与链接。没有 PR/SHA 就用 `null` 并说明；负责人没有确认就写
`待分配`，不能拿提交作者猜负责人。失败和等待保留原始证据，不能改成通过。

技术验收 SHA、组合审查/CI head 和部署 merge SHA 分别注明；复用证据须说明源码相同或覆盖范围，
不能把旧 head 的测试写成新 head 重跑。固定生产窗口记录起止时间、总体样本和目标场景样本；
零相关样本不算通过，主线程转述且暂无可引用明细时明示来源和缺口。草稿迁移的编号、表数与兼容
验证只描述草稿，不能与已应用数据库混写；已部署修复仍可等待用户本机反馈。

记录必需内容：稳定 ID、标题、两种状态、负责人、PR/SHA、迁移、UI/API/schema/test 关联、
部署与生产验收、风险、下一步和回退条件。每个关联槽使用 `recorded` / `pending` / `na`、
`refs` 和 `note`；`recorded` 仅表示有记录，具体通过/失败及范围必须读 `note`。
缺少关联显式写 `pending`；不适用写 `na` 并解释，不用空数组假装通过。

```bash
python3 scripts/check_project_handoff.py
python3 -m unittest discover -s scripts -p test_project_handoff.py
node scripts/check-doc-links.mjs
```

检查器只核对必需字段、枚举、SHA/HTTPS 形式、仓库内文件存在、索引及弃用关联；报告待补项但不因
它们失败。它不联网、不验证外链可达性/本地锚点，不从正则推断 UI/API/数据库运行正确，不证明
生产、审批或功能 100% 跑通。现阶段手工运行，不新增 CI 阻塞、不替代或绕过既有门禁。

## 多人协作与契约变更

- 每任务独立分支/worktree；在 PR 指明模块和文件范围、负责人或待分配。修改共享 DTO、路由、
  schema、docs 索引或模板前，与同文件任务协调归属；不得覆盖并行工作。
- 契约变更在现有 PR 模板记清：调用方（UI、SDK、外部 API、后台任务）、字段默认值/省略/null/空值、
  权限、错误码、兼容读写、替代路径，以及 UI→API→DB→刷新读回/缓存的验证缺口。
- 数据库仅增量迁移：先核对远端与其他 PR 的编号、完整文件名、表列、顺序和校验和；新文件优先未占用
  编号。注明旧写入方/新读取方兼容、锁等待、重试、回退条件。历史已部署 SQL 字节不得改写。
- 合并前 fetch 真实 `play/main`；用普通 merge 在任务分支解决冲突，逐文件保留双方语义，记录真实父提交、
  最终 SHA 和差异，并重跑受影响门禁/复审。不得 force/rebase；门禁和发布权限仍以交付流程为准。
- 回退触发条件包括权限放宽、账务不一致、迁移失败、部署 SHA 不符或健康异常。停止继续推进，由主线程
  协调经审查的源码回退/revert；不得用清空策略或删除数据代替回退。记录部署 check、健康/API 与三身份
  用户本机验收，失败/缺失继续保留。精确命令及审批边界复用交付流程和同步手册。

## 弃用与移除

1. 先盘点 UI、route、API、service、schema、后台任务、外部调用方、历史数据和替代路径。只因上游缺失、
   路由数不同或暂时无调用，不能自动认定废弃；本轮源独有路由逐条分类见迁移账本。
2. 在快照 `deprecations` 记录稳定 ID、关联功能 ID、状态、负责人、决策原因/版本/证据、调用方与数据盘点、
   替代及迁移说明、兼容期/监控、移除批准、分层移除范围和保留测试。候选先用 `设计`，批准弃用后才标
   `deprecated` / `弃用中` 并更新 API/用户说明。
3. 兼容期依据实际调用方迁移安排确定，不自动设删除日期。监控旧入口调用、失败率和数据差异；确认替代
   路径可用后，再请求明确批准移除范围。没有证据的监控写待补，不能写零调用。
4. 获准后分层移除 UI/route/API/service/schema 的相关代码及失效引用；同步索引和定制登记并保留历史决策。
   历史回归、兼容读取和升级测试按风险保留；失效测试必须解释替代验证，不为“变绿”删失败测试。
5. 删列、删数据、不可逆清理必须另行取得明确授权并完成备份/恢复验证，不自动执行；已部署 SQL 不改写，
   数据演进另增迁移。旧上游归属、Go module/import、LICENSE、作者和必要历史不属于批量清理对象。

`deprecations` 与功能记录通过 `feature_id` 关联；每个弃用中/已移除条目都须有决策，已移除必须有
`removal_approval` 证据。本流程本身不批准移除任何现有功能、API 或数据。
